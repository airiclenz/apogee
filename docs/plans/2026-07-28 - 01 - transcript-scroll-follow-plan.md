## Design decisions (2026-07-28, from the issue + apogee-code parity)

- **Follow is positional: attached ⇔ the view is at the bottom.** One plain flag; while
  attached every repaint ends at the tail, while detached the offset is left alone so the
  view holds exactly where the user put it. This is the apogee-code model (`userScrolledUp`,
  `chat.ts:3631`).
- **Flag polarity and name: `detached bool`**, replacing `userScrolled` (`model.go:156`).
  Zero value = attached = follow — a fresh `Model` follows without construction help, and
  the five existing re-arm sites keep their `= false` shape. Semantics genuinely change
  (today's flag means "suspend sticky-to-top until submit" and is never cleared by
  scrolling), so the rename is the honest move, not churn. Plain `bool`, per ADR 0011.
- **Sticky-to-top survives as the short-reply case plus the sticky header.** The current
  pin (`SetYOffset(off)` on every repaint, `model.go:1768`) is the direct cause of the bug:
  once a reply outgrows the screen the offset stays at the prompt and the tail streams out
  of view. But the existing trailing-blank padding (`model.go:1761-1766`) means
  `GotoBottom()` on the padded lines lands at `max(promptRow, realBottom)`: a reply shorter
  than the screen still shows its prompt pinned to the top (padded bottom = prompt row); a
  longer one follows the tail while `applyStickyHeader` (`model.go:1897-1932`) — which is
  already purely positional, keyed off `YOffset()` — overlays the owning prompt at row 0.
  layout.md's "last user prompt must stick to the top" clause is satisfied in both regimes,
  exactly as in apogee-code where stick-to-bottom and the sticky prompt header coexist.
- **Detach is exact `AtBottom()`, not a pixel threshold.** apogee-code uses "within 40px of
  the bottom counts as at-bottom". A terminal scrolls in whole lines and every scroll
  primitive (wheel, PgDn, viewport keys) clamps at the bottom, so bubbles' `AtBottom()`
  (`viewport.go:187-191`, "at or past the very bottom") is reachable and unambiguous. No
  threshold constant.
- **Programmatic-vs-user discrimination is structural, not flag-based.** apogee-code has a
  known pitfall: any code that writes `scrollTop` directly (its `chat.ts:1044`) can flip the
  follow flag, because detach lives in a DOM `scroll` listener that cannot tell user from
  program. In apogee the ONLY detach site is `scrollViewport` (`model.go:699`), the funnel
  user input goes through; `refreshViewport`'s own `GotoBottom`/`SetYOffset` calls never
  pass through it. Keep it that way — no repaint may ever set `detached = true` (the one
  exception runs the other direction: a clamp that lands the view back on the bottom may
  clear it, item 1).
- **The five re-arm events stay.** `submit` (`model.go:784`), `startNewSession`
  (`model.go:888`), `/continue` (`model.go:948`), `flushInterjections`
  (`interject.go:266`), `resumeLoaded` (`sessions.go:341`) all force `detached = false` —
  the counterpart of apogee-code's `role === 'user'` reset (`chat.ts:1918-1921`): sending a
  prompt means "I'm done reading history".
- **Out of scope, pre-existing:** resize while detached keeps the raw absolute offset across
  a rewrap (visible content can drift; today's behaviour, unchanged). No "jump to bottom"
  affordance/button (apogee-code has none either; the wheel or PgDn re-attaches). Drag
  auto-scroll at the viewport edge stays deferred (CHANGELOG).

## The ground (verified 2026-07-28 against the working tree)

**The policy.** `refreshViewport` (`model.go:1743-1769`) runs on every content repaint and
is the only scroll-policy site. Three branches today: `userScrolled` ⇒ `SetContentLines`
only (position held); no user prompt yet (`rendered.lastUserStart < 0`) ⇒ `SetContentLines`
+ `GotoBottom()`; otherwise ⇒ compute `off := wrappedOffset(lines[:lastUserStart], width)`
(`render.go:645-665`), pad with trailing blanks so `off + Height()` is reachable, then
`SetContentLines` + `SetYOffset(off)` — the sticky-to-top pin. Every appending Update path
funnels here: `eventMsg` (`model.go:322-325`, tokens/messages/tool events), `presentedMsg`,
`cancelledMsg`, `errMsg`, `compactDoneMsg`, `beatMsg`-when-noted, and `layout()`
(`model.go:1689-1706`) ends with it, so resize repaints apply the same policy.

**The input funnel.** `scrollViewport` (`model.go:696-707`) is the single place
`m.viewport.Update` is called; it sets `userScrolled = true` on any offset delta — including
a scroll that lands exactly at the bottom — and nothing ever clears it except the five
re-arm sites. Call sites: `tea.MouseWheelMsg` in every state (`model.go:497-502`),
`pgup`/`pgdown` intercepted in every state (`model.go:628-632`), and the inert-state key
fall-throughs (`model.go:693`, `model.go:732`) which expose the viewport's whole default
keymap there.

**The viewport.** Stock `charm.land/bubbles/v2@v2.1.0 viewport.Model` (`model.go:77`,
constructed at `model.go:172-173`, `SoftWrap = true`). Relevant API: `AtBottom()`
(`viewport/viewport.go:187-191`), `GotoBottom()` (`:590`), and the `SetContentLines` clamp —
shrinking content past the offset silently snaps to bottom (`:260`).

**The sticky header.** `applyStickyHeader` (`model.go:1892-1932`) overlays the user block
owning the top row, computed from `m.viewport.YOffset()` and the stashed
`m.lines`/`m.userBlocks` (`model.go:1748-1749`) — no dependence on the flag. It engages
automatically once the follow offset passes the prompt row; no change needed in this plan.

**Existing tests to revise** (all `internal/tui/model_test.go`, section at `:1875`):
`TestStickyPinsLastUserPrompt` (`:1885-1912` — pins the prompt AND asserts the
`userScrolled` freeze), `TestMouseWheelScrollsWhileIdle` (`:1917-1944` — asserts
`userScrolled` flips true), `TestStickyPinsShortReply` (`:1950-1962` — short-reply padding;
must keep passing as-is in spirit), `TestStickyHeaderHandoffOnScroll` (`:1964-2000` — drives
`SetYOffset` with `userScrolled = true`). Harness conventions: `newTestModel(t)` at 80×24,
`step(t, m, msg)` one-Update helper, content driven either directly
(`m.transcript.addUser/commitAssistant` + `m.refreshViewport()`) or through `step(t, m,
eventMsg{Event: domain.TokenEvent{...}})`; assertion helpers `firstVisibleLine` (`:1879`),
`firstViewLine` (`:1946`), `plain` (`:76`).

## 1. Follow the tail — refreshViewport policy and the `detached` flag — ✅ DONE (2026-07-28)

NOTES (2026-07-28): a FIFTH existing test needed revising beyond the four listed —
`mouse_test.go:TestTranscriptSelectionOnStickyHeaderRow` clicked row 0 expecting the removed pin to
put the prompt line there. It now parks the view on the prompt row explicitly (`detached = true` +
`SetYOffset(lastUserBlock.start)`), keeping its assertions verbatim; the underlying point — mouse
coordinates address the CONTENT lines, not the sticky-header overlay drawn over row 0 — is
pre-existing (it already held whenever the human had scrolled) and is now simply the default state
for a reply taller than the screen.

**What.** The repaint policy inverts from pin-to-prompt to follow-the-tail, preserving the
short-reply prompt pin through the existing padding.

- `internal/tui/model.go:156`: rename `userScrolled` → `detached`, doc comment: the human
  scrolled off the tail; hold the scroll position instead of following new content, until a
  re-arm event (or, after item 2, a scroll back to the bottom).
- `refreshViewport` (`model.go:1743-1769`) becomes two branches:
  - `detached` ⇒ `SetContentLines(rendered.lines)` as today; then, if the clamp inside
    `SetContentLines` left the view at the bottom (`m.viewport.AtBottom()`), clear
    `detached` — the invariant "detached ⇔ not at the bottom" stays total when content
    shrinks under a held offset. Growth never triggers this (offset unchanged, not at
    bottom).
  - attached ⇒ keep the existing padding computation VERBATIM for the has-prompt case
    (`off := wrappedOffset(...)`; pad `lines` so `off + Height()` is reachable,
    `model.go:1759-1766`), `SetContentLines(lines)`, then `GotoBottom()` instead of
    `SetYOffset(off)`. On padded short content the bottom IS the prompt row (pin
    preserved); on long content it is the real tail (the fix). The `lastUserStart < 0`
    branch collapses into this one (no padding, `GotoBottom()` — behaviour identical to
    today's `model.go:1754-1758`).
- The five re-arm sites keep their shape, renamed with comments updated to the follow
  vocabulary: `model.go:784`, `model.go:888`, `model.go:948`, `interject.go:266`,
  `sessions.go:341` — each `m.detached = false`.
- `scrollViewport` (`model.go:703-704`) is renamed mechanically in this item
  (`m.detached = true` on offset delta — old semantics preserved); its real change is
  item 2. Comment blocks describing sticky-to-top (`model.go:690-698`, `:1731-1742`,
  `mouse.go:147`) are rewritten to describe follow/detach.
- ADR 0011 discipline: `detached` is a plain `bool`; `TestModelNoBuilderByValue` untouched.

**Tests.** In `model_test.go`, keeping the harness conventions above: a long streamed reply
(driven via `eventMsg`/`TokenEvent` through `step`) ends with the viewport at the bottom —
tail text visible in `plain(m.View())`, `m.viewport.AtBottom()` true — and the owning
prompt overlaid at the top row (`firstViewLine`); `TestStickyPinsShortReply` semantics still
hold (short reply ⇒ prompt at top via padded bottom); with `detached = true` a
`commitAssistant` + `refreshViewport` leaves `YOffset()` unchanged (the held-position half
of today's `TestStickyPinsLastUserPrompt`, re-asserted under the new name); shrinking
content under a detached offset past the clamp re-attaches (`detached` cleared, view at
bottom); `submit` clears `detached` (re-arm smoke). Revise the four listed existing tests
for the rename; `TestWrappedOffsetMatchesViewport` untouched.

**Acceptance.** Green gate passes. Streaming a reply longer than the screen keeps the tail
in view with the prompt as sticky header; a reply shorter than the screen still opens with
its prompt pinned to the top; a manual scroll still freezes the view (old detach semantics
until item 2).

**Commit.** `fix(tui): transcript follows generated output unless the user scrolled away`

## 2. Positional detach and re-attach — scrollViewport — ✅ DONE (2026-07-28)

**What.** Detach stops being a one-way latch: after routing input to the viewport,
attachment is recomputed from position, exactly the apogee-code listener logic
(`chat.ts:3633-3638`) minus the pixel threshold.

- `scrollViewport` (`model.go:699-707`): replace the offset-delta latch with
  `m.detached = !m.viewport.AtBottom()` after `m.viewport.Update(msg)`. Consequences, each
  deliberate: scrolling up detaches (as today); scrolling back to the very bottom
  re-attaches (new — today nothing but a re-arm event ever clears the flag); a scroll on a
  transcript that fits the viewport can never detach (`AtBottom()` is always true there —
  today a stray offset jiggle could latch the flag); non-scroll keys falling through the
  inert-state routes (`model.go:693`, `:732`) recompute harmlessly (no offset change, no
  attachment change, since detached ⇔ not-at-bottom already holds outside this call).
- Doc comment on `scrollViewport` and the key-routing comment at `model.go:690-692`
  rewritten: the viewport follows the tail; any scroll position IS the policy — at the
  bottom means follow, anywhere else means hold.
- No other site changes: `refreshViewport` still never sets `detached = true` (the
  structural programmatic/user separation from *Design decisions*).

**Tests.** Wheel-up from the bottom of a long transcript detaches (`detached` true, offset
off the bottom) — revision of `TestMouseWheelScrollsWhileIdle`; wheel-down back to the
bottom re-attaches and the next streamed token follows (offset back at `AtBottom` after
repaint); `pgdown` to the bottom re-attaches through the keyboard funnel; a scroll landing
mid-history stays detached and a subsequent append leaves `YOffset()` unchanged; on a
transcript that fits the screen a wheel event does not detach. All through the real Update
path (`step` with `tea.MouseWheelMsg` / key constructors).

**Acceptance.** Green gate passes. The full issue behaviour holds end-to-end in the unit
harness: follow while at the bottom, hold wherever the user scrolls, resume following the
moment they return to the bottom or submit.

**Commit.** `fix(tui): scrolling back to the bottom re-attaches transcript follow`
