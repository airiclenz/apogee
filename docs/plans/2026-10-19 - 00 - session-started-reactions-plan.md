**Ratified design calls** (owner, 2026-10-19):
- **Starts:** every engine session boundary fires — construction (fresh, `--resume`, headless/daemon/`/schedule` Firings), `/clear`, `/new`, `/sessions` resume, `/fork`. Delegates never fire. Payload `start`: `new | resume | clear | fork`.
- **Slot shape:** session-start advice is a fenced block inside the session's next user message, ahead of the prompt — never a separate user-role message. Live conversation only, stripped from the record, dropped on resume. ADR 0076 D6 gets a dated amendment.
- **Timing:** advise entries start in the background at the boundary; the first request carrying a new user message waits only for the rest of each entry's timeout.
- **Ship gate:** `advise:` on `session-started` is refused at load (a sentence naming it pending admission) until the apogee-sim arm passes; the slot is reachable now by engine-origin Go handlers (the bench). Enabling is issue `session-start-advise`, not this plan.

## 7. The session-start advise lane

**What:** Recast at the regression check (2026-10-19). Depends on items 3, 4, 5, 6.
**Goal:** at each Session boundary the agent starts every armed advise-class Reaction on `session-started` in the background (D7 timeout, fail-open); the first request that carries a new user message joins them, waiting only for each entry's remaining timeout, and attaches their output, in config order, as leading advice on that user message, committed to the live conversation. No new user message → nothing attached (a mid-Exchange resume attaches to the next prompt). A new boundary discards unattached results. Bypass (`--bypass`) skips the lane (D9). A failure or timeout adds nothing and is reported as other advise failures are. Reachable only by engine-origin Go handlers until `session-start-advise` lands (the user key stays refused by item 2).
**Approach (assumed at the header base):** the session-start lane does not extend adviseUser (its default branch refuses non-argv/webhook handlers with wrongHandler); it dispatches by handler kind itself — an engine-origin Go handler is called directly — and reuses runSyncArgv/runSyncWebhook plus adviceOf/redaction for argv and webhook handlers so the later user-key enable is a validation change only; join in `(*Agent).buildRequest` (`internal/agent/loop.go`) at the point the new user message enters the request; span provenance as the trailer records it.

The boundary only starts the background runs — it never waits, emits or reports on the caller's goroutine (every TUI boundary runs on the Bubble Tea Update goroutine).

Each boundary cancels the previous lane's ctx before starting the next, agent shutdown cancels it, and failures are reported at the join.
