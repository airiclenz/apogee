# The daemon — durable schedules over a declarative file — implementation plan

**Goal:** ship `apogee daemon` per [ADR 0034](../adr/0034-the-daemon-is-an-in-repo-subcommand-over-a-declarative-trigger-action-file.md):
an in-repo subcommand that reads `~/.apogee/daemon/schedules.yaml`, runs each entry's prompt on
its cycle through the shared runner (`internal/run`) and scheduler (`internal/schedule`), saves
every Firing into the shared sessions store, live-reloads the file, refuses a second instance,
and generates the host supervisor's unit via `apogee daemon install`.

**Date:** 2026-08-22
**Status:** unexecuted
**sized for:** ~200k-context host

## Ratified design calls

Decided by the owner (Airic Lenz) in the 2026-08-22 grill session that produced this plan:

1. **v1 scope: core daemon + `install`.** No `apogee daemon add` CLI sugar (the file is the
   contract), no `keep: N` retention, no `at:`/cron anchoring, no webhook triggers, no `mcp:`,
   no request-priority hint (waits on the Gateway). All stay future envelope keys per ADR 0034.
2. **Cycle semantics as the library already states them:** first tick one full cycle after the
   entry is (re)adopted; a daemon restart resets every phase; nothing fires at boot (restart-storm
   protection). No persisted last-fired state.
3. **Reload identity is the entry `name`.** Unchanged (name + spec deep-equal) → untouched,
   phase preserved. Edited → stop + re-add (phase resets). Removed → stopped; an in-flight
   Firing finishes (the library's `Stop` contract). Added → added. Any invalid entry — duplicate
   name included — rejects the WHOLE file with a logged reason; the previous set keeps running.
   No partial swaps.
4. **Schema (the v1 envelope):**

   ```yaml
   shutdown-grace: 10m          # optional, default 10m
   schedules:
     - name: nightly-audit      # required, unique
       on:
         cycle: 24h             # required, >= schedule.MinCycle
       run:
         prompt: "/code-audit internal/tui"   # required, non-empty
         workspace: ~/repos/apogee            # required, must exist at validate
         mode: auto             # optional: plan (default) | auto
         server: openrouter     # optional: a servers: entry name (ADR 0055)
         model: qwen/qwen3-72b  # optional: multi-model entries only (ADR 0055)
   ```

   `mode: auto` entries are validated against the host's Auto-eligibility ladder at load; an
   ineligible host rejects the file (all-or-nothing, the entry named in the log).
5. **Server binding per ADR 0055:** by name into `servers:`; `model:` refused on a
   launcher-fronted entry; the daemon never actuates a load — a Firing against an idle local
   server fails visibly in its record. `config.yaml` is read at startup only; rebinding servers
   is a daemon restart. `schedules.yaml` is the only live-reload surface.
6. **Modes are Plan/Auto only (ADR 0033 wholesale).** A Plan Firing's deliverable is the
   recorded answer (read in `/sessions`); an Auto Firing's is files in the workspace. Stated in
   the seeded template's comments.
7. **Single instance via an advisory OS lock** (`flock` / `LockFileEx`) held for the daemon's
   lifetime on a file under `~/.apogee/daemon/` — self-clearing on crash by construction; the
   PID inside is diagnostics only, never consulted.
8. **Shutdown:** first SIGTERM/SIGINT stops the clock, gives an in-flight Firing
   `shutdown-grace` (default 10m) to finish, then cancels (the runner saves what completed);
   a second signal cancels immediately; exit 0. Generated units derive their kill escalation
   from the grace (grace + 30s).
9. **`install` generates and instructs, never runs the supervisor's CLI.** It writes the unit
   file to the per-user location (or `~/.apogee/daemon/` for the Task Scheduler XML) and prints
   the one activation command. Re-running regenerates and says whether the file changed.
10. **First run seeds a commented `schedules.yaml` template** (embed, never overwritten); an
    empty set is valid — the daemon runs, logs "0 schedules", and watches. Logging is plain
    timestamped lines on stdout; the supervisor owns retention.

## Explicit non-goals (so nothing is re-derived)

Everything in design call 1; IPC of any kind; a daemon-side config.yaml watch; carry-over
context between Firings (a Mechanism, per ADR 0033); courtesy probing of server business
(ADR 0034 decision 9 — the Gateway owns supply).

## 1. `internal/daemon`: the schedules file — schema, parse, validate — ✅ DONE (2026-08-22)

NOTES (2026-08-22): the injected facts are grouped into one `Host` struct (`Home`, `LookupServer func(string) (ServerFacts, bool)`, `AutoEligible bool`) rather than loose parameters; the plan's `autoOK` is spelled `AutoEligible` to match the verdict's existing name in the repo (`domain.ConfinementCaps.AutoEligible`, `probe.HostReport.AutoEligible`).

NOTES (2026-08-22): one exported entry point — `Load(data []byte, host Host) (File, error)` — with parse and validate as unexported halves, so a caller cannot forget the second; a PARSE failure returns the parse defects alone (validating a half-decoded document would report absences the file does not have), while every validation defect is reported together via `errors.Join`.

NOTES (2026-08-22): added one strictness rule beyond the listed set — a second YAML document is refused (internal/config `Document`'s reasoning: the decoder reads only the first, so entries after a `---` would be edited and never fire). Same rationale as the unknown-key rule the item states.

NOTES (2026-08-22): the ADR 0055 `model:`-on-launcher rule consults `LookupServer` with the entry's `server:` value verbatim; an entry with no `server:` asks with the EMPTY name (the host's startup default), and a lookup that cannot answer for it skips the rule rather than inventing an unknown-server defect — so a caller wiring item 6 cannot accidentally refuse every default-bound entry.

NOTES (2026-08-22): no CHANGELOG entry for this item — plan item 9 owns the daemon's single `[Unreleased]` feature entry.

**What:** new package `internal/daemon` holding the file model and its validation, pure and
host-free. Types mirroring the design-call-4 schema (`File{ShutdownGrace, Schedules}`,
`Entry{Name, On{Cycle}, Run{Prompt, Workspace, Mode, Server, Model}}`), parsed with strict
field checking (unknown keys are defects — this file is hand-edited, and a typo that parses is
a schedule that silently never changes). Validation returns ALL defects, not the first
(`ValidateServers`' reasoning, stated in its doc: a defect outlives the day it was written).

Rules: unique non-empty `name`; `cycle >= schedule.MinCycle`; non-empty `prompt`; `workspace`
required, `~`-expanded, must exist and be a directory; `mode` ∈ {plan, auto} (absent = plan);
`shutdown-grace` positive when present (absent = 10m). The config/host-dependent rules take
injected facts so the package stays pure: a `func(name string) (ServerFacts, bool)` lookup
(exists; is launcher-fronted) for `server:`/`model:` (ADR 0055: unknown server, or `model:` on
a launcher-fronted entry, are defects), and an `autoOK bool` for `mode: auto` entries.

**Files:** `internal/daemon/doc.go`, `internal/daemon/file.go`, `internal/daemon/file_test.go`

**Tests:** table-driven: a valid two-entry file parses to the expected model with defaults
applied; each rule above produces its named defect; multiple defects are all reported; an
unknown key is a defect naming it; `~` expansion resolves against the injected home.

**Acceptance:**
- `go build ./internal/daemon/`
- `go test ./internal/daemon/ -count=1`

## 2. `internal/daemon`: the reload diff — name-keyed, phase-preserving — ✅ DONE (2026-08-22)

NOTES (2026-08-22): the diff's result is FOUR name lists on a `Reload` struct (`Kept`, `Replaced`, `Added`, `Removed`) — the item says "three name-lists" but enumerates four (keep, replace, add, remove), and add and remove are distinct operations a reload log must distinguish (a rename shows up in both).

NOTES (2026-08-22): `Apply(scheduler, ids, running, desired) (Reload, error)` computes the diff itself and returns it, rather than taking a precomputed one — a caller cannot then hand it a plan derived from a different pair of sets. `Diff(running, desired) Reload` stays exported and pure for logging, tests and a future `daemon check`.

NOTES (2026-08-22): the Entry→Spec mapping is the method `Entry.Spec()` (idiomatic Go, reads at the call site) rather than a package-level `SpecFor`; it lives in diff.go as the item says.

NOTES (2026-08-22): added `Reload.Changed()` — item 7's reload log needs the "no change" verdict (a reordering or comment edit keeps every entry), and the question belongs beside the diff rather than re-derived at the log line.

NOTES (2026-08-22): `Apply` treats a Stop that returns `schedule.ErrNotFound` as satisfied rather than a failure — the entry is off the clock, which is what the stop asked for; every other Stop or Add failure is wrapped with the entry's name and joined, and none of them stops the remaining operations. A name with no id in the map is never stopped (its own Add failed earlier).

NOTES (2026-08-22): `Reload` is documented as the DECISION the diff made, not a report of what landed — an entry whose Add failed is still listed in `Added` and is named in the returned error, and is absent from the name→id map.

NOTES (2026-08-22): edited `internal/daemon/doc.go` (not in the item's Files list) because the package doc carries the file map every file must appear in; it gained the diff.go line and a short "Reload by name" section stating the phase-preserving rule.

NOTES (2026-08-22): no CHANGELOG entry for this item — plan item 9 owns the daemon's single `[Unreleased]` feature entry.

**What:** the pure diff design call 3 specifies, plus its application. `Diff(old, new []Entry)`
returns three name-lists — keep (deep-equal), replace (same name, changed spec), add/remove —
and `Apply` walks a minimal scheduler interface (`Add(schedule.Spec) (string, error)`,
`Stop(id) error`) plus the daemon's own name→id map to enact it: stop removed and replaced
entries, add new and replaced ones, touch kept entries not at all. Apply is what makes "editing
one schedule re-phases nothing else" true, so it is tested against a fake scheduler recording
the exact call sequence. The `Entry → schedule.Spec` mapping (name, cycle, prompt, mode) lives
here too — the daemon-only `run:` fields (workspace, server, model) travel to the Firing
composition via the name→Entry map, not through the library's `Spec`.

**Files:** `internal/daemon/diff.go`, `internal/daemon/diff_test.go`

**Tests:** table-driven diffs (kept/edited/removed/added, and an entry renamed = remove+add);
Apply against the fake: kept entries receive no calls, replaced entries stop-then-add, the
name→id map ends correct; an Add error surfaces without wedging the remaining operations.

**Acceptance:**
- `go test ./internal/daemon/ -count=1`

**Commit:** `feat(daemon): name-keyed reload diff that preserves unchanged phases`

## 4. `internal/platform`: the advisory single-instance lock — ✅ DONE (2026-08-22)

NOTES (2026-08-22): the refusal is an exported type — `platform.LockHeldError{Path, PID}` — rather than a message a caller parses. The item asks for "an error naming the path and, best-effort, the PID … the caller turns that into 'apogee daemon is already running (pid N)'"; a type is how item 6 composes that line from fields instead of text. A `PID` of 0 means the file carried no readable number and the rendered message simply omits the parenthetical (covered by a test). Non-refusal failures (open failed, the lock call itself failed) stay plain wrapped errors naming the path, so `errors.As` cleanly separates "someone has it" from "it broke".

NOTES (2026-08-22): on Windows the lock is taken over ONE byte at offset 1 TiB — past end-of-file, which is legal and does not grow the file — not over the file's contents. Windows byte-range locks are mandatory rather than advisory: a range another handle holds exclusively cannot even be read, so locking the contents would hide the PID from exactly the process that must print it (the loser of the race) and from a human running `type schedules.lock`. POSIX needs no such care — flock constrains nothing but other flock callers.

NOTES (2026-08-22): took the item's "second descriptor" branch for the conflict test rather than a helper subprocess: flock keys on the open file description and LockFileEx keys on the handle, so a second `AcquireLock` of the same path inside one process is a real kernel conflict on both platforms. The subprocess idiom would have tested the same kernel behaviour with more moving parts.

NOTES (2026-08-22): `release` is `sync.Once`-wrapped (idempotent, per the item's test list) and drops the lock explicitly before closing — Windows releases a closed handle's locks eventually rather than promptly, so an explicit `UnlockFileEx` is what keeps a restart from losing the race to its own predecessor. It never unlinks the lock file: removing it would let the next caller lock a deleted inode while a live holder still had the real one. Its two failures are unreported by design (the signature is a bare `func()` and release runs on the exit path); the discards are `_ =` with the reason stated at `releaseLock`.

NOTES (2026-08-22): `internal/platform/doc.go` needed the file-map upkeep its `docmap.Check` test enforces — the three new files named, "Eighteen files, in three groups" → "Twenty-one files, in four groups" (the lock is the fourth), plus a paragraph on why the lock is a platform facility at all.

NOTES (2026-08-22): no CHANGELOG entry for this item — plan item 9 owns the daemon's single `[Unreleased]` feature entry (items 1–3 did the same).

NOTES (2026-08-22): the Windows and darwin halves are verified by cross-compilation only — `GOOS=windows|darwin go vet ./internal/platform/` (which type-checks the test file too) and `CGO_ENABLED=0 go build` for windows/amd64, windows/arm64, darwin/arm64 — since this host is Linux. The behavioural assertions (a second acquisition conflicts, the PID stays readable while held) ran on Linux; owner-run confirmation on the other two hosts belongs with item 9's live verification note.

**What:** design call 7. `platform.AcquireLock(path string) (release func(), err error)` —
open/create the file, take the OS advisory lock non-blocking (`flock(LOCK_EX|LOCK_NB)` on
unix, `LockFileEx(LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY)` on windows), write the
PID for `cat`-diagnostics, hold the descriptor until release. A held lock returns an error
naming the path and, best-effort, the PID read from the file — the caller turns that into
"apogee daemon is already running (pid N)". No liveness probing, no stale handling: the kernel
drops the lock with the process.

**Files:** `internal/platform/lock.go`, `internal/platform/lock_unix.go`,
`internal/platform/lock_windows.go`, `internal/platform/lock_test.go`

**Tests:** acquire → release → acquire succeeds; while held, a second independent acquisition
of the same path fails with the path (and pid) in the error — via a second descriptor where
the platform's semantics make that a real conflict, else a helper subprocess (the stdlib's own
idiom); release is idempotent.

**Acceptance:**
- `go build ./internal/platform/`
- `go test ./internal/platform/ -run 'TestAcquireLock' -count=1`

**Commit:** `feat(platform): advisory single-instance file lock`

## 5. The Firing composition: one validated entry → one run — ✅ DONE (2026-08-22)

NOTES (2026-08-22): the composition is a `*daemonWiring` whose `fire(ctx, schedule.Firing)` IS `schedule.Config.Fire` — one value item 6 plugs straight into `schedule.New` — rather than a per-entry closure built at adoption as the item's wording suggests. `schedule.Config.Fire` is scheduler-wide, so a per-entry closure could only be reached through a name→closure map the daemon would have to invent; the wiring therefore owns the name→Entry map itself (`adopt` replaces it wholesale per accepted reload, `entryFor` reads it under an RWMutex because Firings run on the Scheduler's goroutines while a reload swaps it on the watcher's). This is the map `internal/daemon/doc.go` already anticipates: "those fields reach the Firing composition through the daemon's own name→Entry map instead."

NOTES (2026-08-22): the wiring splits host-resolved-once from entry-resolved-per-Firing, per ADR 0055's "config.yaml is read at startup only": `newDaemonWiring` resolves the options, the validated `mechanisms:` list, one shared `config.KeyResolver`, the `newConfiner()` backend and the sessions store; `configFor` resolves the server, the model overlay, the workspace roots, the key and the per-model spec per Firing.

NOTES (2026-08-22): the Confiner is composed on EVERY Firing, not only Auto ones — headless does the same, and a Plan Firing's terminal commands are held to the same posture a session's are. The Auto-eligibility gate is deliberately NOT re-run here: item 1's validation already applied it (`Host.AutoEligible`) at the surface that offered the mode, so the composition trusts `Firing.Mode` exactly as `scheduleWiring.fire` does.

NOTES (2026-08-22): added the fan-out width beyond the item's literal list — `config.ResolveParallelAgents(server.ParallelAgents, discoverSlots(...))`, the bound entry's pin over the same one-shot probe headless uses, with a pin skipping the probe. Omitting it would have left every daemon Firing running its delegations one at a time beneath a host whose sessions and headless runs fan out several, which is the ADR 0031 "every Driver reaches the same engine behaviour" invariant rather than an optional extra.

NOTES (2026-08-22): the options copy handed to `rebindSpecFor` is overlaid exactly as `liveSettings.rebindInputs` overlays it (endpoint, key, resolved window pin, resolved response-reserve share), spelled inline because a daemon has no live-settings holder — without the endpoint overlay every input keyed on the endpoint (the probe record behind the identity ladder, and so the Validated-set decision above it) would resolve against the startup server while the Firing dialled another one.

NOTES (2026-08-22): the "no launcher actuation" requirement is pinned two ways — a behavioural test that a launcher-fronted entry's endpoint and empty model reach the runner untouched, and `TestDaemonFireCompositionNamesNoLauncher`, which parses `daemonfire.go` and fails on any identifier containing "launcher". A behavioural test cannot prove an actuation that never happens; the structural one can.

NOTES (2026-08-22): a Firing whose schedule name is no longer in the adopted set is refused with a named error rather than fired (the tick was due while the entry left the clock); `serverFor` likewise refuses a `server:` no `servers:` entry answers to, a branch validation already prevents but which would otherwise mean firing at the wrong server after a config/schedules drift.

NOTES (2026-08-22): edited `cmd/apogee/doc.go` (not in the item's Files list) because `TestDocMapNamesEveryFile` fails on a file missing from the package's file map; it gained the `daemonfire.go` line beside `schedule.go`.

NOTES (2026-08-22): no CHANGELOG entry for this item — plan item 9 owns the daemon's single `[Unreleased]` feature entry (items 1–4 did the same).

**What:** `cmd/apogee/daemonfire.go` — the daemon's counterpart to `scheduleWiring.fire` and
`runHeadless`'s composition, built once at adoption per entry and handed to the scheduler as
its `Fire`. Per design call 5 / ADR 0055: resolve the entry's server (named `servers:` entry,
else the startup default `selectStartupServer` yields), overlay `model:` where legal, resolve
the per-model half through `rebindSpecFor` exactly as headless does, leave Asker/Presenter nil
and MCP unwired, run through the `runOnce` seam, and map the result onto `schedule.Outcome`
(answer, denials, usage, record id) so the Notify log can state what happened. Auto entries
compose the Confiner via the `newConfiner` seam — same gate headless applies, already proven
at validate-time by item 1's `autoOK` fact. No launcher actuation anywhere on this path.

**Files:** `cmd/apogee/daemonfire.go`, `cmd/apogee/daemonfire_test.go`

**Tests:** with `runOnce` stubbed: a plain-server entry composes endpoint/model/key from its
named entry; `server:` absent falls to the startup default; a launcher-fronted entry sends to
its endpoint as-is (no actuation call sites exist to stub — assert by construction: the test
compiles against a composition that takes no launcher seam); Plan and Auto map to the modes
`run.Once` receives; the Outcome carries the stubbed result's answer and denial count.

**Acceptance:**
- `go build ./cmd/apogee/`
- `go test ./cmd/apogee/ -run 'TestDaemonFire' -count=1`

**Commit:** `feat(daemon): per-entry firing composition over the shared runner`

## 6. `apogee daemon`: the command — startup, lifecycle, logging — ✅ DONE (2026-08-22)

NOTES (2026-08-22): DECISION (a) — `daemonHost`'s `LookupServer` answers for the EMPTY name with the startup default's facts (`IsLauncherFronted: opts.StartupLauncher != ""`, the flattened `llama-launcher:` of the selected `servers:` entry), so ADR 0055's `model:`-on-a-launcher-fronted-server rule reaches default-bound entries — the entry most people write first — instead of silently skipping them. Pinned two ways: a table over the lookup itself (empty / plain / fronted / unknown) and `TestDaemonHostRefusesAModelOnTheLauncherFrontedDefault`, which drives the refusal through `daemon.Load`.

NOTES (2026-08-22): DECISION (b) — the daemon closes its Confiner on the way out. The teardown is a new `(*daemonWiring).closeConfiner() string` in `daemonfire.go` (a file item 5 owns) rather than a reach into `w.confiner` from `daemon.go`: the field belongs to the wiring, and returning the notice instead of printing it keeps "where the daemon narrates" in `daemon.go`. It makes the same optional-`Close() error` assertion and runs the same `platform.ConfinementTeardownNotice` as `wire.go` and `headless.go`. It is deferred immediately after `newDaemonWiring`, so every later refusal leaves through it too; `daemonfire.go`'s `confiner` field doc gained the one clause pointing at it.

NOTES (2026-08-22): the grace wait counts in-flight Firings in the daemon itself (`firingTracker`, fed by the fired/completed/failed events the log already renders) rather than reading `Scheduler.List()`. It has to: `Stop` removes a Schedule from `List` immediately while leaving its in-flight Firing to finish, so at the exact moment a shutdown needs the answer the library's own surface has stopped giving it. The tracker only signals while draining, so an idle moment between two cycles cannot let a shutdown skip a grace it should have waited out.

NOTES (2026-08-22): shutdown stops the clock via `daemon.Apply(scheduler, ids, running, nil)` — item 2's diff against an empty desired set — rather than a hand-rolled loop over the id map, so the stop path and the reload path enact a removal the same way. The running set it diffs from is the entries the id map actually holds, so an entry whose Add failed is never stopped.

NOTES (2026-08-22): the plan's "`Scheduler.Close` on a grace timer" is spelled Stop-all → wait → `Close`. `Close` cancels the context every Firing runs under and joins, so calling it first would cancel the in-flight Firing the grace exists to protect; the ordering is the only reading of design call 8 the library supports.

## 7. Live reload: watch, validate, swap — ✅ DONE (2026-08-22)

NOTES (2026-08-22): DECISION followed — the watch is folded into `runDaemon`'s existing wait rather than sitting beside it. The bare `<-daemonStopRequest(...)` became `for { select { case <-stopRequested: shutdown; return / case _, watching := <-changes: reload } }`, so the loop is single-threaded: a save being acted on finishes before the stop is read, and a stop already asked for is never overtaken by a save. A `changes` channel that closes on its own sets the case to nil and logs it, because a closed channel in a select is a busy loop, not an end.

NOTES (2026-08-22): the watch is reached through a seam — `var watchSchedules = func(path string) (<-chan struct{}, func())`, defaulting to `filewatch.New(path)` started — rather than a direct call. What this item owns is what the daemon DOES when a save lands; the poll cadence, the settle window and the two witnesses are internal/filewatch's own tested behaviour (item 3), and a test of the reload should not have to out-wait 1.25s of real time per case to reach it. The production default is therefore covered by the live run below rather than by a unit test.

NOTES (2026-08-22): kept the reload in `daemon.go` rather than taking the item's `daemonreload.go` option. It is ~110 lines including doc comments, daemon.go is mid-sized for the package (574 lines against headless.go's 732 and wire_settings.go's 1127), and the file's package comment already frames its contents as the lifecycle — seed, lock, load, adopt, reload, shut down — which is exactly where a reload belongs.

NOTES (2026-08-22): the item's "one adopt function, called with an empty previous set at startup" is `adoptSchedules(scheduler, wiring, ids, running, desired)` = `daemon.Apply` + `wiring.adopt`. It adopts the desired set whatever Apply reported, because the id map — not the returned `Reload` — is what says who is on the clock: an entry whose Add failed is absent from that map and can never fire, while withholding the set on a partial failure would leave the entries that DID land with no workspace to run in.

NOTES (2026-08-22): `loadSchedules` was split rather than duplicated — `readSchedules` is the read + validate + log-every-defect half both callers share, and each caller words its own refusal (startup: "nothing was scheduled; fix the file and start again"; reload: "the edit was refused whole — keeping the previous N schedules on the clock").
