Deepening the agent loop and its seams

The engine is well-shaped at the large scale — the single runner in internal/run, the one-responder provider seam, the ADR-0010 module order. The friction concentrates where a deep module was declared but its logic stayed scattered across thin siblings. Six deepening candidates follow.

▢ solid = module —— seam → leak deep module

One write-funnel for safety + undo

Strong in-process

Problem. Adding one write tool composes six-plus helpers across three packages by hand, and the undo capture is re-invoked at four separate mutation sites (copy, move, delete each call capturePreImage+commit themselves), so the "one funnel" guarantee ADR 0051 promises holds only because tests discipline pin it — a new verb that omits the capture line silently falls out of /undo with no compile-time signal.

Solution. One deep writeFunnel module that executes a body function while marshalling path-safety → permit → capture → OS write → journal atomically, and every writer of the family lands on it.

wins
  • · Locality: verdict, safety, capture concentrate in one module
  • · A new write tool cannot silently lose /undo coverage
  • · Deletion: six hand-composed helpers vanish, none reappear
  • · Interface shrinks; implementation absorbs the funnel

Collapse the 19-Mechanism boilerplate

Strong in-process

internal/mechanisms/{grammar · decompose · toolfilter · toolresultcap · readloop · filehint · cot · guideddecomposition · emptyresponse · validate · syntax · autofix · readrepeat · toolloop · truncatehistory · errorenrich · cachedcontent}.go · catalogue.go

before

Skeleton ~80% every Mechanism
× 19 near-empty constructors + descriptor literals

after

registerMechanism(hook, descriptor, deps) — one deep home

Problem. Every Mechanism repeats the same five-part template — init, register row, empty struct, trivial constructor, hook closure — differing only in descriptor values and one hook method; only a handful need injected dependencies, yet each file re-spells the register ceremony.

Solution. A shared registerMechanism in catalogue.go that fills the descriptor and constructor by convention, dropping the ~19 near-empty newZ one-liners and the identical post-response ActionRetry{Inject} delivery.

wins
  • Deletion test: 19 constructors are pass-throughs — complexity vanishes
  • Locality: the Mechanism shape is owned once, not nineteen times
  • Catalogue and descriptor cannot drift
  • New Mechanism = one hook + one row, not five parts

Make the registry the one config home

Strong in-process

internal/config/registry.go · config.go (keyAccessors) · options.go · defaults/ · cmd/apogee/wire_boot.go · cmd/apogee/wire_settings.go

before · 5 tables to step

registry row · keyAccessors · fileConfig · apogee.Config · applySettingFor

→

after · one registry row spells it

registry carries flag/env/projection/apply — one home

Problem. Every config key is hand-described twice — once as a registry row, once as a parallel keyAccessors closure for from-file/from-env/from-flag — plus a fileConfig field, an Options field, a wire projection line, and a live-apply switch case; so "adding a key" is a five-table surgery and the registry's "single source of truth" claim is only true about the path, never the resolution.

Solution. Fold the source metadata (flag, env, apply, projection) into the registry row and generate the rest from it, so a new key lands as one row — with a coverage test that fails when a row has no Config field or no apply case.

wins
  • Leverage: one row pays back across every surface
  • Adding a key stops being a five-table restatement
  • Bijection guard would pin behaviour, not just the path

One composer for every unattended run

Strong in-process

cmd/apogee/headless.go:386 · schedule.go:81 · daemonfire.go:222

Problem. The same "compose an unattended run's apogee.Config" is written three times — headless, the TUI-hosted Schedule, and the daemon each carry ~150 near-identical lines — drifting a hair per Driver on secret env vars, extra read roots, and response reserve.

Solution. One shared composer firingConfig(binding, workspace, mode, delegates) used by all three Drivers — a single home for the unattended-run shape ADR-0031 already declares one shared runner for.

Type the diff tools' outcome — stop re-parsing prose

Worth exploring in-process

internal/tui/diffbody.go (regions) · internal/tools/git.go · internal/tools/view_diff.go · internal/domain/toolsummary.go · internal/tools/diff.go

Problem. git_diff_range never attaches a typed outcome at apply time, so the TUI re-walks the rendered diff prose back into regions — restoring the exact ADR-0011 anti-pattern the edit tools solved with typed EditRegions — and the wire' tag triple lives chopped across three files, string-typed with no import.

Solution. Attach a typed domain.DiffStat to git_diff_range like the edit tools do, and export the shared tag constants from the seam so one move can't leave a set behind.

ADR

Re-aligns with ADR-0011 (the view stays a thin renderer) — the recovery hooks exist only because the tool carries no typed summary, so this deepens rather than reopens the ADR.

wins
  • The diff's facts live with the tool that computed them
  • Renderer stops re-deriving the regions from prose
  • Seam stays typed: tag constants travel, not strings

Stop persisting the TUI's render shape in the codec

Worth exploring in-process

internal/tui/transcriptcodec.go · internal/tui/transcript.go · internal/domain/toolsummary.go

Problem. The transcript codec re-encodes the TUI's render shape — EditRegions/RegionFiles — into the session record, directly contradicting domain's "never persisted in the Session record" contract; it exists only to keep a diff's shape across a restart, which replay already carries.

Solution. Persist only the already-rendered stacked Details rows; the codec stops carrying a presentation copy the engine owner explicitly disowned.

ADR

Contradicts the domain's "EditRegions are never persisted" contract — worth fixing because the persisted rows add a second home a schema change must find.

wins
  • Session record stops holding presentation bytes
  • One fewer serialized copy of the region fact
  • Surface and engine contract re-align

Top recommendation

Tackle the write funnel first — it is the daily cost of the whole safety axis. Today adding one write tool is a six-helper, three-package assembly and the /undo guarantee is a test-discipline fiction, not a construction guarantee. One deep writeFunnel collapses the top three findings into one module, passes the deletion test on every shallow copy helper, and directly raises the seam's test surface: a new write verb positively gains path-safety, permit, and journal interplay by construction. When it lands, the config consolidation (candidate 3) is the strongest runner-up for broadest per-key leverage.
