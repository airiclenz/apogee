---
title: "ADR 0096 amendment of 2026-10-17: daemon Firings layer their own Project config"
---

Decided by the owner on 2026-10-17 and shipped by plan `2026-10-17 - 00` item 5 (issue
`daemon-project-layer`). It amends decision 4's daemon sentence — "the daemon reads no Project
config at all … per-firing layering is a follow-up" — which stays in the decision as the record of
what was first decided. Nothing else in decisions 1–7 changes.

- **Each Firing layers its own workspace's Project config.** A daemon Firing resolves the Project
  root of its Schedule entry's workspace (decision 1) and overlays that root's
  `.apogee/config.yaml` on a copy of the daemon's startup Options, under the same key classes and
  precedence as a session (decisions 6 and 7): project parameters and tighten-only additions take
  effect, global-only keys are ignored. The daemon's own Options are never changed, so two
  Schedules in two workspaces never see each other's layer — the leak decision 4 named is closed by
  layering per Firing, not per process.
- **The project file is read fresh at each Firing.** An edit to a workspace's Project config reaches
  that workspace's next Firing without a restart; the daemon watches nothing new for it.
- **The startup resolve stays global-only and is read once (ADR 0055 kept).** `apogee daemon`
  still resolves `~/.apogee/config.yaml` alone at startup, never its start folder's Project config,
  and it captures the global document then; every Firing's overlay merges into that captured
  document, so the global file is never re-read per Firing and a config edit still needs a restart.
- **Notices are latched per Project root and notice text.** A project file that does not parse,
  holds a value its key refuses, or states a global-only key costs one line in the daemon log the
  first time a Firing layers it, not one per Firing; a second workspace's trouble, or an edit that
  changes the complaint, is still said.
- **Proposals stay inert and silent.** Allow rules remain unanswerable in the daemon: a Firing runs
  Plan or a fenced Auto and never reaches the ordinary gate an Allow rule answers (decision 3), so a
  proposed rule is neither offered nor logged there, and `apogee project adopt` stays the way to
  answer one from a terminal.
- **Still out of scope.** In-session `/schedule` Firings keep the session's live options, and the
  execution keys (`mcp-servers:`, `reactions:`) stay global-only, as ADR 0076's 2026-10-10
  amendment left them.
