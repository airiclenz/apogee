---
title: "ADR 0076 amendment of 2026-11-09: the request-tail advise slot at pre-request and post-response"
---

Ratified by the owner on 2026-11-09 for plan `2026-11-09 - 01 - non-tool-advise-slot-plan` (issue
`non-tool-advise-slot`). Decisions 5, 6 and 7 stand as first written; on these points this
amendment fixes decision 6's non-tool slot for the two seams that are not tool-shaped:

- **`pre-request` and `post-response` take `advise:`.** A user `advise:` entry (argv, webhook or
  MCP) on either seam validates and arms; `history-rewrite` still refuses it, and its refusal
  sentence points to `pre-request`, which reaches the request after a rewrite. The slot meets
  `adr-0076-amend-1021`'s structural bar, so the user cell opens without an admission arm; such an
  arm stays welcome evidence, never a gate.
- **Decision 6's "fenced user-role message appended at the tail" is fixed per tail role.** The
  advice lands on the outgoing request's last message, placed by that message's role
  (`Request.AdviseTail`): a tool-result tail takes a **trailing fence inside that tool message**; a
  user tail takes a **leading fence inside that user message**, as session-started advice does; an
  assistant tail gets **one new user message holding only the fence**. Never a fold into the system
  message — the `InjectContext` adjacency decision 6 closes stays closed. The Rejected row "a
  dedicated tail message for every advise" holds: only an assistant tail gains a message, and no
  user-role message is ever placed after a tool result.
- **Request-only lifetime.** The fence lives on the request copy alone (the `Request.NoteOnTail`
  precedent): never in the conversation, the snapshot, the session record or the Defer queue, and
  gone from the next request. The request prefix up to the advised message is untouched, as
  decision 6 requires.
- **Ordering.** On one tail the advice fence sits ahead of the engine-note rows, so a capped
  delegate's wrap-up directive stays last; post-response advice held for a request lands ahead of
  that request's own pre-request advice.
- **Firing.** Both run synchronously through the Reaction cascade, fail-open under
  `domain.DefaultAdviseTimeout` (decision 7). pre-request advice lands on the request it fires for
  and re-runs whenever that request is rebuilt (an overflow fold, a fallback switch). post-response
  advice is held, Exchange-scoped, and lands on the Exchange's next request; an answer to a final
  reply reaches no request, because the Exchange's end drops it. A command, webhook or MCP tool
  reads the seam document with the request, or the response, under `value` in the shape the
  seam-closing notice carries.
- **Visibility, Bypass, delegates.** Each firing books a `ReactionFiredEvent` with action `advise`
  (`/advice`), never a transcript row; `bypass:` switches the entries off and drops held advice; a
  delegate inherits them, as it inherits post-tool-result advice.
