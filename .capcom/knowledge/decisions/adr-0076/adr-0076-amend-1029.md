---
title: "ADR 0076 amendment of 2026-10-29: the mcp: handler"
---

Ratified by the owner on 2026-10-29 for plan
`2026-10-29 - 01 - mcp-reaction-handler-plan` (issue `mcp-handler-posture`). Decision 3's sentence
"`mcp:` handlers are **reserved** likewise … the key is held and the posture decided when a case
arrives" and the rejected-list row "`mcp:` handlers now, inheriting the tool's posture" are settled
here. The case has arrived, and the posture is **authorship trust, not inheritance**: the call
never takes the MCP tool's own approval posture, because the user who wrote the entry has already
approved it. The Approver collision decision 3 named does not arise, since no prompt is ever raised
inside a prompt. Decision text stays as written; ADR 0034 decision 5 is left untouched (it governs
the daemon schedule's `run:`, not Reaction handlers).

Decided by the owner:

- **The case.** An `advise:` entry at `session-started` calling a llama-launcher status tool, so the
  session opens knowing which model is loaded; an observe entry is the second case.
- **Trust: authorship is the approval.** A user Reaction's `mcp:` call never reaches the Approver.
  The user authored the entry, so writing it is the approval; no per-call prompt is raised.
- **Classes.** `run:` (observe), `advise:` and `gate:` all accept `mcp:`. Gate rules are unchanged:
  a gate never says yes, and a gate whose handler fails escalates to ask.
- **Drivers without MCP.** headless, daemon and bench Firings dial no MCP server; in them an `mcp:`
  entry is inert with one notice per entry, never a load error.
- **Gate without MCP.** In a Driver with no resolver, advise and observe `mcp:` entries are dropped
  before arming. An `mcp:` gate stays armed and escalates to ask without calling anything, so a
  Firing's deny-all Approver refuses every call it gates.
- **Confinement.** The call runs with `confine-to-workspace` on, spawns no process, and an advise
  answer is secret-redacted like any other advise answer.
- **Shape.** A handler mapping with an `mcp:` key is an MCP handler, one with `url:` a webhook:
  `{mcp: {server:, tool:, args:, payload-arg:}}`. `args:` is static. `payload-arg:` puts the
  SeamPayload JSON object under that argument name; naming a key `args:` already holds is refused
  at load.
- **Results.** The tool's text blocks, joined, are the answer, read as argv's stdout is. An
  `isError` result, a timeout, a server that is not connected, a missing tool and a pin-skipped
  server are each a handler failure.
- **Engine seam.** `domain.MCPHandler` is pure data; the Driver injects a resolver, and the engine
  never imports `internal/mcp` (ADR 0031's wire-silent engine).
- **Repo scope.** An adopted repo entry (ADR 0104) may name only a server its own Project config
  declares and does not shadow; a global entry may name any server.
- **Record.** This amendment is the record.

Decided by the plan writer within those calls:

- **Resolver shape.** `domain.MCPResolver func(server, tool string, project bool) (MCPCall, error)`
  and `MCPCall func(ctx, args json.RawMessage) (string, error)`. The answer is the joined text with
  no `(mcp tool returned no content)` placeholder, so an empty answer stays silent advice.
- **Notice cadence.** A resolution failure (no server, no tool, wrong layer, pin-skipped) is
  reported once per entry per Agent; a call failure (`isError`, timeout) is reported every time, as
  argv's is.
- **Inert-notice wording.** "MCP servers are not connected in this run" — true for headless,
  daemon, probe and a TUI `/schedule` Firing alike.
