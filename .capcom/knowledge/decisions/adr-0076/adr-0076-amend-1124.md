---
title: "ADR 0076 amendment of 2026-11-24: the question-asked notice, the denied count, and no approval-requested where nobody is asked"
refs: [internal/domain/events.go, internal/reactions/runner.go, internal/domain/ask.go]
---

Decided by the owner on 2026-11-24 (issue `ntfy-push-notifications`). Decision 1 stands as first
written; on these points this amendment extends its notice list for a question put to the human, and
adds two facts to what the observe lane reports:

- **`question-asked` is a notice, fired before the question is answered.** Decision 1's notice list
  gains it, last, after `compaction-finished` (`domain.MomentQuestionAsked`). It fires wherever the
  engine puts a question to the human through the **Asker** and waits on it, from four points: the
  `ask_user` tool, a recipe's prompt for a required input its launch text left unbound, a foreground
  Workflow `ask` stage (asked through the same recipe prompt), and a background Workflow `ask` stage
  once it queues in the session's background prompts (ADR 0089), stamped with the Turn that launched
  the workflow. Each emits before the question queues for the prompt slot an Approval may hold, as
  an Approval's requested phase is emitted before the Approver is consulted, so an observer learns a
  human is being waited on while the wait is still happening. Its payload carries `question`,
  `choices` (absent for a free-text question), `multi_select` and, for a question a child asked,
  `sub_agent_name`. It is a `run:` notice only — not an `advise:` Moment. `ask_user` is withheld
  from sub-agents, so the notice is top-level in practice. Where no Asker is configured — `apogee
  headless`, daemon and `/schedule` Firings — nothing is asked and nothing fires.
- **It rides a new Event variant, `domain.QuestionEvent`, not an `ObserveRunner` door.**
  `adr-0076-amend-1021b` published `compaction-finished` through the Driver's `ObserveRunner` so
  that ADR 0018 decision 6's "no new Event variant" held for a fold, which is history maintenance a
  Driver need not show. A question is the opposite case: the engine itself puts it to the human, it
  is the Asker's counterpart of `ApprovalEvent{Phase: ApprovalRequested}`, and a Driver or the Event
  journal has to fold it — a watcher otherwise sees a session that stopped for no visible reason. So
  it is an Event every sink sees (the sealed sum type grows additively), and it gets its own journal
  line, `question` (`adr-0075-amend-1124`). `ask_user` builds its request one interface boundary
  away from the Agent that knows the Turn and owns the sink, so the Agent installs a per-call
  carrier, `domain.WithQuestionAnnouncer`, beside `WithConsoleOwner`, and the tool reports through
  `domain.AnnounceQuestion` (a no-op where none is installed); the recipe and background paths emit
  directly.
- **A matcher-only mapping was rejected.** The notice could have been derived without a variant —
  a `ToolCallEvent` for `ask_user` plus a `WorkflowPhaseEvent` in its `waiting` phase. That misses
  the recipe's missing-input prompt, which emits neither; it fires on a tool call before `ask_user`
  validated its arguments, so a malformed call would announce a question that is never asked; it
  would tie the notice to a tool's name; and it would leave the journal and the Drivers with no
  Event for a question, which is the half a Driver needs.
- **No `question-answered`, for now.** `approval-decided` was added cheaply because the engine
  already emitted both phases of an Approval (A6). A question has no such second Event: its answer
  is the asking call's own result — the `ask_user` tool result in the transcript, the bound recipe
  input, the stage's output — and a question can also end unanswered (a cancel), so an honest
  `question-answered` would need an answered-versus-abandoned phase of its own. Nothing in this
  issue needs it; it can be added additively later as a second notice.
- **`exchange-finished` carries `denied`.** The Runner counts every `ApprovalEvent` decided with
  `deny` — by a human, or by an unattended run's no-one-to-ask denier — at every depth, and writes
  the count onto the `exchange-finished` payload, always, `0` included; no other notice carries the
  field. The count resets at every Depth-0 Turn boundary that is not a plain `turn-complete` (an
  Exchange that closed, a cancel), so a cancelled Exchange's refusals never leak into the next. A
  gate Reaction's `deny` is no Approval and is not counted. A TUI background workflow's refusal
  made while no Exchange is open counts toward the next Exchange that closes. The count lives on
  the Runner, not the stateless matcher, so it survives a live `Replace`.
- **Unattended roots fire no `approval-requested`.** A root built by the binary's `raise` —
  `apogee headless`, a daemon Firing, a `/schedule` Firing — always ends in `run.Once`, whose
  denier refuses every gated call the moment it is raised, so an `approval-requested` Reaction there
  would announce a wait that never happens. `reactions.HostOptions.Unattended` (facade
  `ReactionHostOptions.Unattended`), set in `raise` and nowhere else, makes the Runner drop those
  firings. The engine's `ApprovalEvent`s are unchanged and still reach the decorated sink, so the
  headless `approval` lines carry both phases; `approval-decided` still fires there, with the
  `deny`. This changes what a configured `approval-requested` entry does in those runs, which
  pushed a notice for a wait nobody was in; a user who wants news of a refusal there subscribes to
  `approval-decided`.
