---
title: "ADR 0024 amendment of 2026-11-11: a failed rebind is retried on the next beat"
refs: [internal/tui/heartbeat.go]
---

One sentence of the Decision no longer describes the renderer in full: "a landed beat is measured
against the last **observation**", which left an identical beat rebinding nothing even after a
rebind had failed. The rest stands.

- **A failed rebind is retried on every later beat.** The observation was recorded before the
  rebind seam answered, so a refusal (a model still loading, a prompt file mid-edit) left an
  identical next beat measuring as "nothing new" and the session stuck on the old binding — or,
  after a failed first contact, with no model bound at all — until the human acted. Now, while
  `heartbeatState.lastRebindFailed` is set, `Model.observeBinding` treats every landed beat as a
  change and asks the `ServerHost.Rebind` seam again. `Model.applyRebind` is the one place that
  sets the marker, for every caller (a beat at idle, the deferred `pendingRebind`, a `/model`
  pick); a success clears it, as do `followFallback` and the wholesale reset of a `/server` switch.
- **No backoff.** The beat is already `heartbeat.Interval` (60 s) apart, and the seam reads local
  files.
- **The refusal is still noted once per distinct target**, however many beats retry it; the retry
  that lands writes the ordinary note — `model changed: …`, or `connected: …` after a failed first
  contact, which is not a quiet first-contact seed.
- **A retry on a windowless beat keeps the last known window.** A retry that fires only because the
  marker is set, on a beat reporting `ContextWindow == 0`, keeps the observed window and carries it
  on the rebind intent: a windowless beat names no window, so a successful retry must not bind — and
  announce — an unknown one.

The pin argument is unchanged: a beat is still measured against the last observation whenever no
rebind has failed, so a `context-window:` pin the server keeps contradicting stays "nothing new".
