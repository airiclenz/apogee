---
title: "ADR 0012 amendment of 2026-11-23: path safety resolves through one resolver, and a junction leaving the workspace is an escape"
---

**Why now.** Path safety is one of the two bounds this ADR lets a call run ungated under, and its
resolver stopped short of one kind of link. `security.EvalRealPath` resolved through
`filepath.EvalSymlinks`, which on Windows does not cross an NTFS junction: for a path under a
junction it fails, and the old climb then answered with the junction's own spelling. So
`security.ResolveInRoot` compared both sides unresolved, and a junction inside the workspace
pointing outside it did not read as an escape. Five resolvers had grown around the same question,
each junction fix patching one caller (issue `real-path-five-resolvers`; plan
`docs/plans/2026-11-23 - 00 - real-path-one-resolver-plan.md`, items 1–2).

**(a) One resolver.** "Where does this path really live" is answered by the leaf package
`internal/realpath`, which imports nothing internal. `internal/security` holds no resolution logic
of its own: `EvalRealPath` keeps its name and is a one-line delegate to the leaf.

**(b) Junctions are crossed.** A junction is resolved like a symbolic link, never treated as
opaque. `security.ResolveInRoot` on a path under a junction that leaves the root returns
`ErrPathEscape`; a junction that stays inside resolves to its target's spelling. The blast-radius
bound path safety gives is therefore the same on Windows as on POSIX.

**(c) Two entry points.** `realpath.Resolve` is strict: it fails on a missing path, with
`filepath.EvalSymlinks`' own `fs.ErrNotExist`-classed error. `realpath.ResolveLenient` never fails:
it climbs to the nearest existing ancestor, resolves that and re-joins the rest, so a file about to
be created is still judged at a real location. Path safety uses the lenient one.

**(d) One spelling.** On Windows `ResolveLenient` always answers with the volume's final path name,
junction or not, so two separately resolved paths compare in one spelling; when that call fails for
every ancestor it falls back to the `Resolve` climb. Visible change: on a subst or mapped-drive
workspace an absolute resolved path shows the underlying location. Both sides of a containment
comparison must come from `EvalRealPath`, never one side from another resolver. The Project config
refusal (ADR 0096 §5) keeps holding under that rule: `security.ProjectRootPaths` carries the root's
final-name spelling (`FinalRoot`) beside `Root`, and the rule refuses the config through either.

**Unchanged.** ADR 0020's rule stands: a Windows box root that is a reparse point is refused, never
resolved through. `ErrPathEscape`'s sentence is byte-identical. The Windows proof is the
`test-windows` CI job (`internal/security`, `-run 'Junction'`).
