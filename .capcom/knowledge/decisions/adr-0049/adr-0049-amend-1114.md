---
title: "ADR 0049 amendment of 2026-11-14: remote, url, protocol and submodule keys that reach a program"
---

`adr-0049-amend-1103` lists the keys a repo-local `git config` write names `.git/config` for, and
the side each lives on. This note widens that list on both sides (items 1 and 2 of
`docs/plans/2026-11-14 - 00 - git-remote-program-keys-plan.md`, issue `git-remote-program-keys`,
after the Medium finding "Git command-config denylist omits keys that make git run a program" in
`docs/reviews/code-audit-2026-11-10.md`). The rule that splits the keys is amend-1103's, unchanged:
a key apogee's own git can reach goes in the probe source; a key the git hosts already neutralise
per verb goes in the write view's suffix only.

**Probe source: `remote.<n>.vcs`.** `GitCommandConfigNameSource` gains `remote.<n>.vcs` (any remote
name, matched lowered), beside `remote.<n>.proxy`. Its value names a remote helper, and git resolves
a slashed name (`a/b`) against the working directory, so `remote.origin.vcs = a/b` runs a planted
`./git-remote-a/b` on the git actions host's fetch: no per-verb option stops it. gitexec's probe
therefore refuses a repository carrying the key, naming it, and both the git tool and the git
actions host decline to run git there. No `GIT_ALLOW_PROTOCOL` allowlist was added (owner,
2026-11-14).

**Write-view suffix only.** `GitCommandConfigName` gains these names, matched lowered, and never in
`GitCommandConfigNameSource`:

- `remote.<n>.uploadpack` and `remote.<n>.receivepack`: the program run on the far side of a local
  or ssh transport.
- `protocol.allow` and `protocol.ext.allow`: they open the `ext::` transport, whose URL is a command
  line. No other `protocol.<x>.allow` name matches.
- `url.<base>.insteadOf` and `url.<base>.pushInsteadOf` only where `<base>` starts with `ext::`: the
  only rewrite that names a program, since a URL-form helper name cannot carry a slash.
- `submodule.<n>.update` only for a value starting with `!`, which git runs as a command.

The git actions and status hosts neutralise every one of these per verb (`-c protocol.ext.allow=never`,
`-c protocol.git.allow=never`, `--upload-pack=git-upload-pack`, `--receive-pack=git-receive-pack`,
`-c submodule.recurse=false` with `--recurse-submodules=no`), so the probe would cost a repository its
git tools for keys that reach no program of apogee's. But the operator's next ordinary git honours
them, so a shell `git config` line that sets one into the repository's own config gains `.git/config`
as a write target and `write-git-control-plane` hard-refuses it, as amend-1103 describes.

**What stays clear.** Amend-1103's rule extends to two more value exemptions, read in
`gitConfigValueIsBenign` (`internal/security/shellwrites.go`) beside the `core.fsmonitor` boolean
one: a `protocol.allow` or `protocol.ext.allow` whose value lowers to `never` hardens rather than
opens, and a `submodule.<n>.update` mode that does not start with `!` (`none`, `rebase`, `merge`,
`checkout`) names no program. Neither exemption applies under a removal form (`--unset`,
`--unset-all`, the `unset` subcommand), whose next word is a value-pattern, not a value: a removal
stays a write for every key, the new families included. Other `protocol.<x>.allow` names, non-`ext::`
rewrites such as `url.git@github.com:.insteadOf`, a `--global` write and every read form stay clear,
as before. `mergetool.<tool>.path` and `difftool.<tool>.path` stay out, like `alias.*`: git runs them
only when the operator types `git mergetool` or `git difftool`.
