---
title: "ADR 0105 amendment of 2026-11-02: an Anthropic api_error counts as 500"
---

Decided with the Server fallback follow-ups (docs/plans/2026-11-02 - 01 - fallback-followups-plan.md, item 1). It amends decision 3 for the Anthropic `api_error`.

Decision 3 named the Anthropic `overloaded_error` as a 529 and left every other Messages slug a plain terminal fault. That missed the `api_error`, which is that wire's 500: a mid-stream `api_error` ended the Turn with neither a re-stream (ADR 0082 D2) nor a move to a fallback, where the same fault framed as an HTTP 500 gets both. **An `api_error` counts as 500.** `classify` gives a code-0 in-band `api_error` the 500 it stands for, as it gives a `rate_limit_error` its 429, so the one `isTransientFault` rule reads it as retryable and `UpstreamFault.FallbackEligible` as eligible, and its fault text reads `in-band error 500:`. Every other Messages slug the rule does not name (`authentication_error`, `permission_error`, `not_found_error`, …) stays a plain terminal fault, as decision 3 says.

The stub keeps the two wires in step: stubllm renders `api_error` only for a scripted 500, and an unlisted code below 500 as `invalid_request_error`, so a fixture's 4xx stays terminal on the Messages wire as it does on the chat wire.
