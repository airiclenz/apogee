---
title: "ADR 0095 amendment of 2026-11-22: a stored token matches on its client id too"
---

Recorded on 2026-11-22 by the MCP holder consolidation run (docs/plans/2026-11-22 - 00 - mcp-holder-consolidation-plan.md, item 3), closing `mcp-oauth-assembly`. The code has held this rule since 2026-10-14 (`40ff8b30`, a `client-id:` change treated as a missing login); this amendment writes it into the record. It amends D1.

**D1 — a stored token is used only under the configuration that minted it.** The record is still one file per server, its stem the server's name, and its storage key does not change: no record is renamed or migrated. What changes is the match condition a loaded record must pass before its token or refresh token is sent. A record is used only when its server name and its normalised endpoint match the configured ones, as D1 already said, **and**, when the entry sets `client-id:`, the record's client registration carries that same client id. A record issued to another client is `mcpauth.ErrLoginRequired`, exactly as a record minted for another endpoint is a miss, so a changed `client-id:` needs a new login and a refresh never pairs the stored client id with a new `client-secret-env:` secret. A dynamically registered client (no `client-id:`) matches on name and endpoint alone. The issuer is the fourth condition and is set by `adr-0095-amend-1111` D9: with `issuer:` configured, a record another issuer minted, or one naming no issuer, is `ErrLoginRequired` too.

All four facts — store, endpoint and its pinned client, client id with its secret, and issuer — are assembled in one place, `mcp.OAuthBinding` (`internal/mcp`), into one `mcpauth.Binding` that `apogee mcp login` and connect both use, and `mcpauth`'s `clientMatches` and `issuerMatches` are the rule's one implementation (`docs/design/mcp-client.md`).
