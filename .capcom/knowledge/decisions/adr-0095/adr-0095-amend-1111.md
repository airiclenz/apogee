---
title: "ADR 0095 amendment of 2026-11-11: a client secret goes only to a pinned issuer"
---

Decided by the owner on 2026-11-11 and shipped in the PDF parser fork and defects run (docs/plans/2026-11-11 - 00 - pdf-parser-fork-and-defects-plan.md, items 10 to 13), fixing `oauth-secret-unpinned-issuer`. It amends D3 and D9.

**D3 — a client secret needs a pinned issuer.** A confidential client's `client-secret-env:` needs a new `issuer:` key beside `client-id:`: the issuer URL of the authorization server the client was registered with, an absolute `http` or `https` URL with a host and no user info, query or fragment, taken as written. An entry with `client-secret-env:` and no `issuer:` is refused on every layer — at load for the global file, as a dropped entry with a notice for a Project config, and by `validateServers` for an embedder Host — and `mcpauth`'s `Login` and `NewHandler` refuse a client secret with no issuer as well. `issuer:` is optional for a public or dynamically registered client, and legal on any `auth: oauth` entry.

**D9 — the operator may narrow the untrusted authorization server, never widen it.** The MCP server still names the authorization server; with `issuer:` set, a login uses it only if the protected-resource metadata lists it (exact string after trimming space; with no metadata, the endpoint's origin is the only offer) and otherwise fails with `mcpauth.IssuerMismatchError` before any request to an authorization server. That error is the one `Login` error outside its origin redaction: it names the configured issuer and the offered ones by scheme, host and path. A stored token another issuer minted is `ErrLoginRequired`, so neither a refresh with the secret nor the access token is sent. The secret therefore goes only to an authorization server the operator named, never to one an endpoint picked; the authorization server's traffic still runs under the floor exactly as D9 says.
