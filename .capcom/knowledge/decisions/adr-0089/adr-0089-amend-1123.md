---
title: "ADR 0089 amendment of 2026-11-23: a background run that could not start ends like any other"
---

D3 says "when a background workflow ends, the engine emits a finish event". Until this amendment one
ending did not: a background run that failed before its Runner knew its folder — its item source no
longer reads, say, so `Runner.Run` returned no id — held a `workflow <name> failed — <cause>` note
but emitted no event, so a Driver that wakes on the event never woke, and the folder the launch had
opened stayed `pending` and listed as neither live nor finished, which `^r` refused.

**Every ending of a started-or-launched background run emits its event.** A background launch opens
its folder ahead of the run (`Runner.Open`), so it has the id even when the run never reaches it:
the run's end reports under that launch-time id — started, then failed with its cause — after the
note is held, as D3's order already requires. A blocking launch has no such id, and a blocking run
that fails before it has one still reports nothing; only its answer carries the cause.

**A folder that never ran is recorded `failed`.** The library writes it, never the agent
(`internal/workflow` is the only writer of a run's phase): `Runner.Run` marks the folder itself when
it fails after finding the folder, and `Runner.SettleFailedStart` marks it for a caller that has the
launch's id when `Run` failed before finding it. Both take the same rule: only a folder recorded
`pending` is written, so a finished folder whose queued re-run could not start keeps its `done` or
`failed`, and a stopped or cut-off one keeps its phase. A folder `Admit` refused is left as it was —
the refusal is another run's claim on the folder, not this run's failure. The failed folder lists
as `failed` and is resumed by a re-run (`RerunFailed`) like one a stage error ended.

A queued run stopped before it started is unchanged: it never started, holds no note and emits no
event (D5; the 2026-10-14 queued-stop rule).
